# BuildFlow — контекст проекта для Claude Code

> Этот файл лежит в корне репозитория и читается в начале каждой сессии.
> Полное ТЗ: `docs/TZ_v0.9.pdf` (предварительная спецификация MVP, версия 0.9 от 10.10.2026).
> При любом расхождении между кодом и ТЗ — сначала спроси, не «чини» молча.

## Что строим
BuildFlow — система управления материальными и денежными потоками строительной компании:
6–10 объектов, отдельный склад на каждом объекте, мобильный доступ для пяти рабочих ролей.
Это **новый проект с нуля**. От прежнего BuildFlow взято только название: его код, схема БД и деплой
не используются, на них не ориентироваться и ничего оттуда не переносить.

**Входит в MVP:** объекты, заявки, закупки, накладные, поставщики, приёмки/выдачи/возвраты,
кассы и счета, долги, бригады, акты работ, задачи, согласования, отчёты.

**НЕ входит (не реализовывать, даже если «просто добавить»):** межскладские перемещения,
кабинет снабженца, CRM продаж квартир, банковский эквайринг, онлайн-рассрочки,
налоговый и зарплатный расчёт.

## Стек (не менять без согласования)
- Next.js (App Router) + TypeScript strict, деплой на Vercel
- Supabase: PostgreSQL, Auth, Storage, RLS
- Интерфейс полностью на русском, responsive, mobile-first
- Окружения: staging и production; CI/CD; секреты только в env, никогда в коде и клиентском бандле
- `service_role` ключ — только на сервере, никогда в клиенте

## Роли
| Код | Роль | Суть |
|---|---|---|
| `accountant` | Материальный бухгалтер | Вносит в систему накладные (поставщики, цены, суммы), сверяет и закрывает заявки, расходы, долги; согласует материалы и услуги. **Заявки не оформляет** (Д-92) |
| `warehouse` | Заведующий складом | Оформляет заявки для снабженца, приёмка факт. количеств (поставщика не указывает, Д-102), выдача, возвраты, остатки. **Не видит закупочные цены** |
| `cashier` | Кассир | Приходы/расходы, несколько касс и счетов, частичные оплаты |
| `foreman` | Прораб | Бригады, задачи, объёмы работ, акты |
| `project_manager` | Управляющий проектом | Объекты, задачи, утверждение актов работ, отчёты **только по закреплённым объектам** |
| `org_admin` | Администратор организации | Учётные записи и доступы (техническая роль) |

## RBAC (предварительная матрица ТЗ, раздел 3)
| Операция | Бухгалтер | Склад | Кассир | Прораб | Управл. |
|---|---|---|---|---|---|
| Заявки | Просмотр, сверка/закрытие | Создать/изменить | — | — | Просмотр |
| Накладные и цены | Создать/проверить | Ограниченно (без цен) | Ограниченно | — | Просмотр |
| Приёмка | Просмотр | Провести | — | — | Просмотр |
| Выдача/возврат | Просмотр | Провести | — | Ограниченно | Просмотр |
| Платежи | Согласовать материалы/услуги | — | Провести | — | Просмотр |
| Работы бригад | Просмотр | — | Просмотр | Создать | Утвердить |
| Задачи | Просмотр | Исполнить | Исполнить | Исполнить | Создать |

Правила:
- Всё ограничено `organization_id` и назначенными объектами (`project_members`).
- Права проверяются **и** в server actions / route handlers, **и** в RLS. UI-скрытие — не защита.
- Скрытие цен от склада — на уровне данных (отдельные view/колонки без цен или column-level grants), а не только в UI.
- Матрица держится в таблицах `permissions` / `member_roles`, не хардкодится в компонентах — она ещё будет меняться.

## Бизнес-процессы
**BP-01 Закупка.** Заведующий складом оформляет заявку (материалы и количества, **без поставщиков и цен**) →
передаёт снабженцу вне системы → склад принимает фактические количества (поставщика не указывает, Д-102) →
бухгалтер вносит в систему накладные (поставщик, цены, суммы) и сверяет их с приёмками → закрытие (бухгалтер).
Одна заявка = несколько поставщиков и несколько накладных (через приёмки и накладные). Решение владельца — Д-92.
Статусы заявки: `DRAFT → ISSUED → PARTIALLY_RECEIVED → RECEIVED → ACCOUNTING_REVIEW → CLOSED`, плюс `CANCELLED`, `DISCREPANCY`.

**BP-02 Склад.** Проведённая приёмка сразу увеличивает остаток. Выдача бригаде уменьшает остаток
с указанием объекта, блока, этажа, бригады. Возврат увеличивает остаток и связан с выдачей.
Расхождение с заявкой хранится отдельно (заказано vs принято).

**BP-03 Поставщики.** Накладные, обязательства, частичные/полные оплаты, остаток долга.

**BP-04 Касса.** Приходы (в т.ч. продажи квартир вручную, средства владельца) и расходы
(материалы, услуги, бригады, зарплаты); выбор кассы/счёта и основания.

**BP-05 Акты работ.** Прораб создаёт акт → отправляет управляющему → управляющий утверждает или отклоняет.
Только утверждённый акт поступает кассиру на полную/частичную оплату. Отклонённый — не поступает.
Согласование бухгалтера для актов бригад **не требуется**. Утверждённый акт неизменяем;
исправление = отмена + новый акт.

**BP-06 Задачи.** Управляющий создаёт задачу (объект, исполнитель, срок, статус); видит только свои объекты.

## Статусы документов
| Документ | Статусы |
|---|---|
| Заявка | см. BP-01 |
| Накладная | Введена; проверяется; подтверждена; отменена |
| Акт приёмки | Черновик; проведён; корректировка |
| Выдача / возврат | Черновик; проведён; сторнирован |
| Счёт | Черновик; согласование; согласован; частично оплачен; оплачен; отменён |
| Акт выполненных работ | Черновик; проверка; утверждён; отклонён; отменён |
| Кассовая операция | Черновик; проведена; сторнирована |
| Задача | Новая; в работе; на проверке; выполнена; заблокирована; отменена |

Каждый документ: номер, организация, объект (если применимо), автор, даты, строки, вложения,
статус, история согласований и аудита. Переходы статусов — только разрешённые (state machine на сервере / в БД).

## Модель данных (целевая, ТЗ раздел 6)
- Доступ: `organizations, organization_members, roles, permissions, member_roles, project_members`
- Объекты: `projects, blocks, floors, warehouses`
- Материалы: `materials, units_of_measure, stock_movements, stock_balances`
- Закупки: `purchase_requests, purchase_request_items, suppliers, supplier_invoices, supplier_invoice_items, goods_receipts, goods_receipt_items`
- Склад: `material_issues, material_issue_items, material_returns, material_return_items`
- Финансы: `cash_accounts, payment_requests, payables, payments, cash_transactions, cash_transaction_allocations`
- Бригады: `crews, crew_members, work_rates, work_completion_acts, work_completion_items`
- Задачи и аудит: `tasks, task_comments, task_attachments, approval_requests, approval_actions, audit_logs, document_attachments`

Обязательно: `organization_id` везде; `project_id` для объектных операций; FK; `NUMERIC` для сумм и количеств
(никаких float/real); явная валюта (по умолчанию TJS) и единица измерения.
Первичные ключи — `uuid` (`gen_random_uuid()`); у каждой таблицы `created_at`, `created_by`, `updated_at`.
Номера документов — человекочитаемые, последовательные в рамках организации и типа документа (например, `ЗК-2026-000123`).

```
src/

  components/ui/       # базовые UI-компоненты

    actions.ts         # server actions (с проверкой прав)
    queries.ts         # чтение данных
    schemas.ts         # zod-валидация
    components/

  tests/               # pgTAP: RLS и функции проведения
docs/
```

## Расчёты и инварианты
- Остаток = начальный + проведённый приход + возвраты − выдачи ± корректировки
- Долг поставщику = подтверждённые обязательства − зачтённые оплаты
- Баланс кассы = начальный + приходы − расходы (± переводы — пока открытый вопрос)
- Стоимость работ = утверждённый объём × договорной тариф; долг по акту = сумма − оплаты
  (пример: 5 000 м² × 30 TJS = 150 000 TJS; оплачено 60 000 → долг 90 000)
- `stock_movements` — источник истины; `stock_balances` — производная, пересчитываемая.
- Проведение **атомарно** (одна транзакция, Postgres-функция) и **идемпотентно** (idempotency key на операцию).
- Проведённое не удаляется: только сторно или контролируемая корректировка, всё в `audit_logs`.
- Приёмка 21 кг при заказе 20 кг: хранятся оба числа, остаток +21 ровно один раз.

Если задача упирается в один из них — реализуй минимально и расширяемо (без «зашитой» бизнес-логики),
пометь `// TODO(TZ-open): ...` и перечисли в итоговом отчёте сессии.

## Правила работы
1. Перед изменениями прочитай затронутый код и текущие миграции. Не угадывай названия таблиц.
   Сгенерированные типы БД (`supabase gen types`) обновляй после каждой миграции.
2. Все изменения БД — только через файлы миграций в `supabase/migrations/`, никаких ручных правок в дашборде.
3. Каждая новая таблица: RLS включён + политики + индексы по `organization_id`, `project_id`, FK.
4. Пока нет боевых данных, миграции можно править. После первого деплоя в production они только добавляются;
   деструктивные (DROP, изменение типа с потерей данных) выполняются только после моего явного «да».
5. Тесты: бизнес-правила и RLS покрываются тестами (Vitest для логики, pgTAP или SQL-тесты для RLS/функций проведения).
6. Не трогать модули вне текущей фазы. Не добавлять зависимости без причины — указывай причину.
7. Конец каждой задачи: `typecheck`, `lint`, тесты зелёные; краткий отчёт: что сделано, миграции, что проверить руками, TODO(TZ-open).
8. Объясняй мне по-русски.
