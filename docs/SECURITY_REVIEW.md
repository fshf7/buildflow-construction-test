# BuildFlow — обзор безопасности (фаза 5, 14.10.2026)

> Что защищаем, чем, как проверяется и что осталось. Ссылки Д-xx — `docs/DECISIONS.md`.

## 1. Модель угроз
| Угроза | Кто | Защита |
|---|---|---|
| Сотрудник видит чужие объекты или данные вне роли | склад, прораб, управляющий | RLS на всех таблицах + права из БД; проверка и в server actions, и в БД (CLAUDE.md) |
| Склад узнаёт закупочные цены | склад | цены — только через `*_priced` представления и column grants; вложения накладных — `prices.view` (Д-24, Д-60) |
| Прямой вызов API в обход UI | любой вошедший | клиенту — только SELECT; запись — SECURITY DEFINER функции с проверкой прав (Д-58); pgTAP 120 проверяет, что DELETE/TRUNCATE у клиента нет |
| Подделка статусов документов, повтор операции | любой | статус меняют только функции (`guard_document`, переходы — каталог); idempotency key на операцию (Д-55) |
| Самосогласование | бухгалтер, управляющий, кассир | согласующий ≠ автор — CHECK + функции (Д-14, Д-67) |
| Захват учётной записи | извне | MFA для администратора и кассира (Д-90); временные пароли с обязательной сменой (Д-88, Д-89); проверка живой сессии (Д-47); лимит перебора паролей (Д-80); регистрация выключена |
| Перебор / злоупотребление | извне, вошедший | лимиты частоты в Postgres (Д-80): вход, восстановление пароля, экспорт, загрузки, импорт, health |
| XSS, кликджекинг | извне | React экранирует вывод; CSP с nonce, `strict-dynamic`, `frame-ancestors 'none'`, X-Frame-Options DENY (Д-81) |
| Утечка секретов | разработка, CI | секреты только в env/хранилищах платформ; `service_role` — только сервер; маскирование в CI; ключи передаются через stdin |
| Утечка ПДн/сумм в мониторинг | — | Sentry со скраббером (Д-83) |
| Потеря данных | сбой, ошибка | ночной зашифрованный дамп + ежедневная проверка восстановлением (Д-82) |

## 2. Доступ к данным (RLS и гранты)
- RLS включён на **всех** таблицах `public` (pgTAP `120_security` — для существующих и будущих таблиц).
- `anon` не имеет грантов на таблицы и не вызывает функции, кроме `health()`.
- `authenticated`: SELECT; INSERT — справочники и структура под RLS (объекты, блоки, этажи, единицы, материалы,
  поставщики, бригады, состав бригад); UPDATE — только перечисленные колонки (column grants) этих же таблиц и
  профиля организации/участника, склада объекта; DELETE — только блоки и этажи объекта (защищены внешними ключами);
  TRUNCATE/REFERENCES/TRIGGER — нет. Документы и деньги — только функциями.
- Все `SECURITY DEFINER` функции — с пустым `search_path` (pgTAP 120).
- Объектный доступ: `private.can(org, project, perm)` = право роли ∧ назначение на объект; MFA-роли без `aal2` — без прав.
- Отчёты — `SECURITY INVOKER` поверх RLS (Д-75): управляющий видит только свои объекты, склад — без цен.

## 3. Аутентификация и сессии
- Supabase Auth без писем (Д-87): сотрудников заводит администратор (логин — телефон или имя; учётная запись на
  технической почте `.internal`, которая не доставляется); регистрация выключена (smoke-тест на staging);
  восстановления пароля по почте нет.
- Временный пароль (Д-88): 14 символов без похожих, криптостойкий генератор; показ администратору один раз, нигде не
  хранится (в Auth — хэш), в аудит — только причина сброса. Минимальная длина пароля в Auth — 10.
- Обязательная смена временного пароля (Д-89): признак в `app_metadata` (меняет только сервер) → proxy пускает только
  на смену пароля, БД (`member_id()` = NULL) не отдаёт данных даже через API; новый пароль ≠ временному.
- Сброс пароля администратором: aal2, своя организация, не себе (себе — `password:reset`); все сессии завершаются.
- MFA TOTP обязателен для `org_admin` и `cashier` (Д-90; бухгалтеру — по желанию): навигация — редирект на `/mfa`, данные — RLS.
- Живая сессия проверяется в БД (Д-47): выход и сброс MFA действуют сразу, без ожидания истечения JWT.
- Сброс MFA — администратором с причиной и записью в аудит (Д-45).
- Cookies сессии ставит `@supabase/ssr`; они читаемы скриптами страницы (так устроен SDK) — риск снижен CSP.

## 4. Ограничение частоты (Д-80)
Счётчик фиксированных окон в Postgres (`private.rate_limits`), ключ — `действие:sha256(значение)`, открытых
email/IP нет. Функцию вызывает только сервер (`service_role`) — прямой вызов из браузера невозможен.

| Действие | Лимит | При превышении |
|---|---|---|
| вход | 10 / 15 мин на IP, 5 / 15 мин на логин | «Слишком много попыток. Повторите через N мин.» |
| экспорт отчётов | 30 / 10 мин на пользователя | 429 |
| загрузка вложений | 60 / 10 мин на пользователя | сообщение |
| импорт справочников | 10 / ч на пользователя | сообщение |
| `/api/health` | 120 / мин на IP | 429 |

Код MFA проверяется напрямую Supabase Auth (из браузера) — действует лимит Supabase на проверки токенов; свой
лимит на него не ставится (отступление от плана фазы). Сбой БД не блокирует пользователя (доступность важнее),
но пишется в лог. Локальные E2E — множитель лимитов, **только** при `NEXT_PUBLIC_APP_ENV=local`.

## 5. Заголовки (Д-81)
`Content-Security-Policy` (nonce на запрос, `script-src 'self' 'nonce-…' 'strict-dynamic'`, `object-src 'none'`,
`frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`, `upgrade-insecure-requests`), HSTS (2 года,
вне локальной разработки), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (камера, микрофон, геолокация — запрещены;
фото с телефона — через выбор файла), `Cross-Origin-Opener-Policy: same-origin`, без `X-Powered-By`.
`style-src` допускает `'unsafe-inline'` (inline-стили компонентов уведомлений) — скрипты inline запрещены.
Проверка: E2E `csp.spec.ts` (нет нарушений CSP в консоли, страницы оживают), smoke staging — заголовки.

## 6. Файлы (Storage)
Приватная корзина `documents`; путь `{org}/{тип}/{документ}/…`; чтение и запись — политики Storage через
`private.attachment_allowed` (сканы накладных — только `prices.view`; задачи — участники задачи; акты — по видимости
акта). Ссылки — подписанные на 5 минут. Типы — PDF и изображения, до 10 МБ.

## 7. Секреты
| Секрет | Где | Кто видит |
|---|---|---|
| `SUPABASE_SECRET_KEY` | Vercel (Sensitive), `.env.local` разработчика | только сервер: создание сотрудников и сброс паролей (Auth Admin), ограничитель частоты |
| `*_DB_URL`, `VERCEL_TOKEN`, `BACKUP_PASSPHRASE` | GitHub environments | workflow; в логах маскируются (в т. ч. перекодированная строка подключения) |
| DSN Sentry | Vercel | публичный по природе (виден в бандле) |
Правило: значения передаются через stdin / скрытый ввод, в аргументы, чат и файлы не попадают.

## 8. Логи и мониторинг (Д-83)
Sentry выключен без DSN. Отправляется: тип ошибки, stack trace, URL без query, внутренний uuid пользователя.
Не отправляется: тело запроса, cookies, заголовки, IP, email/имя, консоль; в текстах вырезаются email, телефоны,
любые числа от 4 знаков и с дробной частью (суммы, количества, номера). Unit-тесты `scrub.test.ts`.

## 9. Бэкапы (Д-82)
Ночной дамп, зашифрованный AES256, 14 копий; ежедневная автоматическая проверка восстановлением и сверкой;
уведомление задачей. Подробно — `docs/BACKUP_RESTORE.md`.
