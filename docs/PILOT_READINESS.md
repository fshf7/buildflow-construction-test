# BuildFlow — готовность к пилоту

> Что должно быть сделано до пилота (ТЗ §9 «Нефункциональные требования», §12 «Условия допуска к пилоту»).
> Обновляется по мере работы.

## Окружения

| | staging | production |
|---|---|---|
| Supabase | проект `construction` (ref `rcinzvflyzjusvrtcivb`, ap-south-1), Free | **нет — нужен до пилота** |
| План Supabase | Free (без бэкапов PITR, письма Auth ограничены) | **Pro — нужен до пилота** (ежедневные бэкапы + PITR, проверка восстановления) |
| Vercel | проект `buildflow-staging`, https://buildflow-construction-staging.vercel.app | нет |
| GitHub environment | `staging` (деплой после зелёного CI, `STAGING_ENABLED`) | `production` создан пустым; деплой только вручную, `PRODUCTION_ENABLED` **не включать** |

### До пилота обязательно (production)
- [ ] Отдельный production-проект Supabase на плане **Pro** (не staging и не бесплатный слот).
- [ ] Ежедневные бэкапы и PITR включены; **тестовое восстановление** проведено и задокументировано (ТЗ §9, §12).
- [ ] Свой SMTP (Resend) с подтверждённым доменом; русские шаблоны писем (`supabase/templates/*`) загружены.
- [ ] Auth: Site URL и redirect URLs — production-домен; регистрация выключена (только приглашения).
- [ ] Vercel: production-проект и переменные приложения; домен.
- [ ] GitHub environment `production`: `PRODUCTION_DB_URL`, `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`,
      переменные `NEXT_PUBLIC_APP_ENV`, `SUPABASE_PROJECT_REF`, `NEXT_PUBLIC_SUPABASE_URL`; затем `PRODUCTION_ENABLED=true`.
- [ ] Обязательный ревьюер production-деплоя недоступен на текущем плане GitHub для приватного репозитория —
      либо план с этой функцией, либо остаётся ручной запуск с подтверждением.

### Staging — что осталось
- [ ] Свой SMTP (Resend): без него письма Auth — 2 в час, а шаблоны писем не меняются. **Ссылки из
      стандартных писем Supabase не подходят приложению** (оно ждёт `token_hash` из наших шаблонов), поэтому
      приглашения и восстановление пароля на staging заработают только после SMTP и загрузки шаблонов.
- [ ] Секреты окружения GitHub `staging`: `STAGING_DB_URL`, `VERCEL_TOKEN` (задаёт владелец вручную); затем
      `STAGING_ENABLED=true` — до этого staging деплоится вручную Vercel CLI (первый деплой 13.10.2026).
- [x] Миграции 1–13 применены, сверка пуста; Auth: Site URL/redirect — staging-домен, регистрация выключена.
- [x] Smoke-E2E против staging (`playwright.smoke.config.ts`): вход, закрытые разделы, экспорт, регистрация, анонимный API.
- [ ] Первый администратор без SMTP — `bash scripts/staging-org-create.sh` (Д-78).

## Условия ТЗ §12

| Условие | Статус |
|---|---|
| Все пять ролей выполняют основные операции | локально — E2E на смартфоне; на staging — после SMTP |
| Разграничение доступа протестировано | pgTAP, интеграционные, E2E |
| Заявки, приёмки, выдачи и возвраты согласованы | фаза 2 |
| Остатки и долги совпадают с контрольными данными | сверочные функции; сверка с реальными обезличенными документами — фаза 5 |
| Частичные оплаты | поставщикам и бригадам |
| Утверждённые акты неизменяемы | триггеры + тесты |
| Повторные запросы не дублируют операции | idempotency keys + тесты |
| Аудит | да |
| Восстановление резервной копии проверено | **нет — нужен production на Pro** |
