# Резервные копии и восстановление

> Supabase Free не даёт восстановимых бэкапов и PITR, поэтому основной бэкап — свой (Д-79, Д-82).
> **RPO ≈ 24 ч** (потеря данных — не больше суток). **RTO** — около 30–60 минут на ручное восстановление
> (уточняется протоколом ниже).

## Как устроено (`.github/workflows/backup.yml`)
Каждую ночь в 03:00 по Душанбе, для каждого окружения, где задана строка подключения:
1. **Дамп** (`scripts/backup/dump.sh`): `roles.sql`, `schema.sql`, `data.sql` (все данные, включая пользователей
   Auth и метаданные файлов Storage), `data-app.sql` (данные приложения — схемы `public`, `private`),
   `counts.tsv` — точное число строк каждой таблицы, `reconcile-source.tsv` — сверка источника.
   Если источник уже не сходится (остатки ≠ движениям и т. п.) — прогон красный: копию с испорченными данными не принимаем молча.
2. **Проверка восстановлением** (`scripts/backup/restore-verify.sh`): чистый Postgres того же образа Supabase
   (временный проект `bf-restore`) ← схема + данные приложения; затем:
   - число строк каждой таблицы = как в источнике (`counts.diff`);
   - сверка (остатки = Σ движений, балансы касс = Σ операций, оплачено = Σ распределений) = 0 расхождений.
3. **Шифрование**: `gpg --symmetric --cipher-algo AES256` паролем `BACKUP_PASSPHRASE` (секрет окружения GitHub).
4. **Хранение**: артефакт GitHub Actions `buildflow-<окружение>-<дата>.tar.gz.gpg`, 14 дней (= 14 копий).
   Лимит артефактов GitHub Free — 500 МБ; при приближении прогон предупреждает.
5. **Уведомление**: сбой → задача «Бэкап <окружение> не прошёл» (письмо от GitHub); повторный сбой — комментарий;
   следующий успешный прогон закрывает задачу.

Проверить уведомление: Actions → Backup → Run workflow → `simulate_failure` ✓.

**Важно:** храните `BACKUP_PASSPHRASE` отдельно от GitHub (менеджер паролей владельца). Без него копии не расшифровать.

## Восстановление вручную

### 1. Скачать и расшифровать копию
```bash
gh run list --workflow Backup --repo officialmanuchehr/construction -L 20      # выбрать прогон
gh run download <run-id> --repo officialmanuchehr/construction -n buildflow-production-YYYYMMDD-HHMM
gpg --decrypt buildflow-production-YYYYMMDD-HHMM.tar.gz.gpg > backup.tar.gz   # спросит пароль
mkdir backup && tar -xzf backup.tar.gz -C backup
```

### 2a. Восстановить в НОВЫЙ проект Supabase (основной сценарий при потере проекта)
1. Создать проект (тот же регион), **сразу**, до запуска приложения.
2. Строка подключения Session pooler нового проекта → `DB_URL` (пароль закодировать или задать через
   `scripts/ci/normalize-db-url.py`).
3. Восстановить (порядок важен; Supabase сам создаёт свои схемы `auth`/`storage`):
   ```bash
   grep -v 'ON PARAMETER' backup/roles.sql | psql "$DB_URL" -v ON_ERROR_STOP=1 -f -   # служебные GRANT — их создаёт сам проект
   psql "$DB_URL" -v ON_ERROR_STOP=1 --single-transaction -f backup/schema.sql
   psql "$DB_URL" -v ON_ERROR_STOP=1 --single-transaction \
     -c "set session_replication_role = replica" -f backup/data.sql
   ```
   `data.sql` включает пользователей Auth — пароли и вторые факторы сохраняются. Файлы Storage (сканы, фото) в
   дамп БД **не входят** — только их метаданные; файлы восстанавливаются из Storage старого проекта, если он доступен
   (`supabase storage cp -r`), иначе ссылки на них останутся без файлов.
4. Сверка: `psql "$DB_URL" -At -F $'\t' -f scripts/backup/sql/reconcile.sql` — всё 0;
   `… -f scripts/backup/sql/table-counts.sql | diff - backup/counts.tsv` — без различий.
5. Переключить приложение: Vercel → переменные `NEXT_PUBLIC_SUPABASE_URL`, ключи; GitHub environment —
   `*_DB_URL`, `SUPABASE_PROJECT_REF`, `NEXT_PUBLIC_SUPABASE_URL`; Auth → Site URL, SMTP, шаблоны (см. RUNBOOK.md).
   Новый деплой (переменные `NEXT_PUBLIC_*` вшиваются при сборке).

### 2b. Откатить ТОТ ЖЕ проект к ночной копии (испорчены данные)
Только после явного решения владельца: всё, что внесено после копии, пропадёт.
Безопаснее: восстановить в новый проект (2a), сверить, затем переключить приложение.
